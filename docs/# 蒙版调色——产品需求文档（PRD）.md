# 二、V1.0 主要问题与本次修订原则  
  
## 2.1 需要修正的关键问题  
  
V1.0 的产品方向是成立的，但存在以下容易在开发阶段造成返工的问题：  
  
1. **HarmonyOS 版本口径不一致**：前文写 HarmonyOS 5.0（API 12）及以上，开发环境又写 API 20 Release 及以上，两个版本口径冲突，需要统一为“最低系统版本”和“实际开发 SDK 版本”两个概念，并以实际 SDK/API 文档为准。  
2. **Core Vision Kit 主体分割能力的输入、输出和蒙版格式描述过于理想化**：不能直接假设 `mattingList` 就可以按原图像素一一对应处理，需要在开发阶段确认实际返回对象、蒙版尺寸、坐标系、透明度/置信度表达方式及 PixelMap 转换方式。  
3. **“背景”定义过于宽泛**：主体分割只能稳定解决“主体/非主体”分区，不能保证天空、地面、建筑等语义区域都能独立识别。因此 V1 不应承诺“天空单独调色”。  
4. **调色算法缺少明确公式和边界**：仅写 RGB-HSV 不足以保证亮度、对比度、色温表现一致，需要定义参数映射、蒙版羽化和边缘混合策略。  
5. **实时预览 ≤100ms 与每次完整遍历原图存在冲突**：如果每次滑动都对原始 1080p/高分辨率图片全量计算，很容易卡顿。需要采用预览缩略图 + 参数提交后高质量渲染的两阶段方案。  
6. **保存成功率 100% 不合理**：文件系统、权限、空间不足、图片损坏等异常不可完全控制，应改为“正常条件下成功率 ≥99.5%”，并定义异常提示。  
7. **“抠图准确率 ≥85%”缺少测试方法**：需要定义测试集、主观/客观评价标准和边缘质量验收方式。  
8. **Worker / TaskPool 方案没有确定边界**：PixelMap 是否可以直接跨线程传递、哪些对象只能在特定线程使用，需要根据实际 API 约束设计。建议将“后台计算抽象层”与具体并发机制解耦。  
9. **V1 功能范围偏大**：服务卡片、跨设备流转不是 MVP 核心能力，建议从首发版本中降级为后续版本，避免影响 9 月上架节点。  
10. **缺少用户授权、隐私、异常和资源释放流程**：图片属于用户数据，必须明确本地处理、最小权限、取消操作、失败恢复、PixelMap 生命周期管理等。  
  
## 2.2 V1.1 修订原则  
  
- **先保证核心链路闭环**：导入 → 主体分割 → 主体/背景调色 → 对比 → 保存。  
- **不夸大 AI 能力**：V1 将“背景”定义为主体之外的区域，不承诺天空、人物皮肤等语义级分区。  
- **先验证 API，再锁定实现**：所有 Core Vision Kit 具体字段、返回结构和版本要求以目标 SDK 官方 API Reference 为准。  
- **预览与导出分离**：实时操作优先保证流畅度，最终导出保证质量。  
- **能力分级**：P0 保证首发，P1 提升体验，P2 在首发后迭代。

# 三、项目概述  
  
## 3.1 项目背景  
  
市面上的图片编辑工具主要分为全能型专业工具和系统级简单编辑工具。前者功能丰富但学习成本较高，后者操作简单但局部调色能力有限。  
  
“蒙版调色”聚焦一个明确场景：  
  
> **利用端侧 AI 自动获得主体/背景蒙版，再让用户分别调整两个区域的颜色参数。**  
  
产品不追求成为全能修图工具，而是通过极简操作解决：  
  
- 人物更亮、背景更暗；  
- 主体保持颜色、背景降低饱和度；  
- 主体更加突出；  
- 背景整体降低存在感；
  
等高频需求。  
  
## 3.2 产品定位  
  
**一句话描述：**  
  
> 像调两个滑块一样简单，分别调整照片主体和背景的颜色。  
  
**核心价值：**  
  
- AI 自动生成主体蒙版，降低局部编辑门槛；  
- 主体和背景独立调色，避免复杂蒙版操作；  
- 图片全程本地处理，减少隐私顾虑；  
- 鸿蒙原生实现，优先适配华为手机体验。  
  
## 3.3 产品目标  
  
| 目标类型 | 具体目标 | 衡量指标                   |  
|---------|---------|------------------------|  
| 用户目标 | 让普通用户在 1 分钟内完成一次分区调色 | 首次核心流程完成率 ≥80%         |  
| 质量目标 | 保证主体边缘和调色结果自然 | 用户评分 ≥4；核心机型无严重花屏/崩溃   |  
| 增长目标 | 上线 30 天获得首批用户 | 累计下载量 ≥400（以实际渠道数据为准）  |  
| 活跃目标 | 建立稳定使用人群 | MAU ≥400，前提是符合当期活动口径   |  
| 性能目标 | 保证编辑过程流畅 | 普通设备预览操作 P95 响应 ≤100ms |  
  
> 注：激励计划的具体报名条件、时间、名额和统计口径可能变化，不能直接作为产品功能验收条件，应以官方活动规则为准。

# 四、目标用户与使用场景  
  
## 4.1 目标用户画像  
  
| 维度 | 描述                 |  
|------|--------------------|  
| 年龄 | 12-65 岁            |  
| 职业 | 学生、职场新人、内容创作者、小微商家 |  
| 设备 | 支持目标系统和主体分割能力的华为手机 |  
| 痛点 | 想做局部调色，但不会复杂蒙版/画笔操作 |  
| 核心诉求 | 快速让主体突出、背景弱化       |  
  
## 4.2 典型场景  
  
### 场景一：人像优化  
  
人物偏暗、背景偏亮。  
  
用户提亮主体并降低背景亮度，使人物更突出。  
  
### 场景二：商品图片  
  
商品本身颜色准确，但背景过于鲜艳。  
  
用户降低背景饱和度，同时保持主体原色。  
  
### 场景三：风景照  
  
> **V1 不将“天空单独调色”作为承诺能力。**  
  
如果 AI 将天空识别为非主体区域，可以通过背景调色间接产生效果，但不能保证天空与其他背景区域被独立处理。

# 六、功能需求  
  
## F1 图片导入  
  
### 功能描述  
  
从系统相册选择一张图片进入编辑流程。  
  
### 交互  
  
1. 首页点击“从相册选择”；  
2. 拉起系统图片选择器；  
3. 用户选择图片；  
4. 显示图片加载状态；  
5. 完成解码后进入 AI 分割阶段。  
  
### 输入约束  
  
- 支持 JPEG、PNG、HEIC 等目标设备系统可正常解码的常见图片格式；  
- 单次仅处理一张图片；  
- 对超大图片进行尺寸控制或分阶段处理，避免直接创建多个超大 PixelMap。  
  
### 验收  
  
- 正常图片可进入编辑页；  
- 不支持或损坏图片有明确提示；  
- 不要求用户授予超出业务需要的权限。  
  
---  
  
# F2 AI 主体分割  
  
## 功能描述  
  
调用 Core Vision Kit 主体分割能力生成主体蒙版。  
  
## 交互状态  
  
| 状态 | 文案 |  
|------|------|  
| 初始化 | 正在准备 AI 能力... |  
| 分割中 | 正在识别主体... |  
| 成功 | 自动识别完成 |  
| 失败 | 未能识别清晰主体，请重试或更换图片 |  
  
## 产品定义  
  
- “主体”指主体分割 API 返回的前景/主体区域；  
- “背景”指原图中主体区域以外的区域；  
- 不承诺所有照片均能获得理想主体；  
- 对主体与背景颜色接近、低清晰度、严重遮挡、复杂多人场景等图片，允许出现识别失败或质量下降。  
  
## 验收测试集  
  
建立不少于 100 张内部测试图片，覆盖：  
  
- 单人正面；  
- 单人半身；  
- 单人全身；  
- 宠物；  
- 商品；  
- 复杂背景；  
- 逆光；  
- 发丝等细边缘；  
- 主体与背景颜色接近。  
  
测试时至少记录：  
  
- 主体大区域是否正确；  
- 主体边缘是否连续；  
- 发丝/细线区域质量；  
- 是否存在明显漏抠；  
- 是否存在明显误抠。  
  
> 不建议继续使用“准确率 ≥85%”作为唯一指标。主体分割是视觉质量问题，应使用测试集 + 人工盲评 + 典型边缘案例组合验收。  
  
## API 注意事项  
  
主体分割的具体初始化方式、配置字段、返回结构、设备限制和版本要求，必须在开发前以当前目标 SDK 官方 API Reference 和真机测试结果为准。  
  
PRD 中的示例代码不应视为永久 API 契约。

# F3 分区调色  
  
## 6.3.1 调色参数  
  
| 参数 | 范围 | 默认值 | 说明 |  
|------|------|--------|------|  
| 亮度 Brightness | -100 ~ +100 | 0 | 控制区域明暗 |  
| 对比度 Contrast | -100 ~ +100 | 0 | 控制明暗差异 |  
| 饱和度 Saturation | -100 ~ +100 | 0 | 控制颜色鲜艳程度 |  
| 色温 Temperature | -100 ~ +100 | 0 | 负值偏冷，正值偏暖 |  
  
## 6.3.2 主体/背景切换  
  
编辑页提供两个 Tab：  
  
```text  
┌───────────────┬───────────────┐  
│      主体      │      背景      │  
└───────────────┴───────────────┘  
```  
  
用户切换 Tab 后：  
  
- 当前参数面板切换；  
- 图片预览区域保持当前位置；  
- 已调整的另一分区参数保持不变；  
- 切换不重新执行 AI 分割。  
  
## 6.3.3 蒙版混合  
  
不能简单执行：  
  
```text  
mask = 1 → 完全使用调色结果  
mask = 0 → 完全使用原图  
```  
  
建议使用连续蒙版权重：  
  
```text  
result = original × (1 - mask) + adjusted × mask  
```  
  
其中：  
  
```text  
mask ∈ [0, 1]  
```  
  
这样可以降低主体边缘出现明显色带、色边的问题。  
  
如果 AI API 只提供二值蒙版，则需要在渲染前增加：  
  
```text  
二值蒙版  
   ↓  
边缘平滑  
   ↓  
羽化  
   ↓  
0~1 权重蒙版  
```  
  
## 6.3.4 调色处理原则  
  
- 所有参数以原图为基准计算；  
- 不对已经调色的 PixelMap 继续叠加处理；  
- UI 滑块改变的是 `EditState`；  
- 预览根据 `OriginalPixelMap + Mask + EditState` 重新生成；  
- 参数全部为 0 时，结果应与原图一致或仅存在可忽略的计算误差；  
- 最终保存必须重新进行高质量渲染。

# F4 实时预览  
  
## 设计原则  
  
不能在用户每移动一次滑块时都对原始高分辨率图片进行完整逐像素处理。  
  
采用两级渲染策略：  
  
### 一级：实时预览  
  
```text  
原图  
 ↓  
缩放到预览尺寸  
 ↓  
应用蒙版  
 ↓  
应用调色参数  
 ↓  
显示  
```  
  
目标：  
  
> 参数变化 P95 ≤100ms。  
  
### 二级：最终导出  
  
```text  
原图  
 ↓  
高质量蒙版  
 ↓  
完整调色  
 ↓  
高质量编码  
 ↓  
保存  
```  
  
这样可以同时兼顾：  
  
- UI 流畅度；  
- 图片最终质量；  
- 内存占用。  
  
## 快速滑动优化  
  
连续拖动滑块时：  
  
- 使用节流；  
- 合并连续参数变化；  
- 取消过期渲染任务；  
- 只保留最新参数；  
- 不允许旧任务覆盖新结果。

# F5 原图对比  
  
支持两种方式：  
  
### 点击对比  
  
点击“对比”按钮：  
  
```text  
原图 → 效果图 → 原图 → 效果图  
```  
  
### 长按对比  
  
```text  
按下 → 显示原图  
松开 → 恢复效果图  
```  
  
对比过程不能重新执行渲染。

# F6 参数重置  
  
支持：  
  
### 重置当前区域  
  
例如当前选择“主体”：  
  
```text  
主体：  
亮度 = 0  
对比度 = 0  
饱和度 = 0  
色温 = 0  
```  
  
背景参数保持不变。  
  
### 全部重置  
  
主体和背景全部恢复为默认值。  
  
重置不需要重新执行 AI 分割。  
  
---  
  
# F7 蒙版查看  
  
建议增加一个轻量的“查看蒙版”入口。  
  
### 正常模式  
  
显示最终调色效果。  
  
### 蒙版模式  
  
```text  
主体：红色半透明  
背景：蓝色半透明  
```  
  
用户可以快速确认 AI 分割是否符合预期。  
  
> 蒙版覆盖不应该长期显示在正常编辑画面上，否则会影响用户判断最终颜色效果。

# F8 保存与导出  
  
## 保存流程  
  
```text  
点击保存  
   ↓  
检查编辑状态  
   ↓  
最终高质量渲染  
   ↓  
图片编码  
   ↓  
写入系统相册  
   ↓  
保存成功  
```  
  
## 成功反馈  
  
```text  
已保存到相册  
```  
  
## 异常处理  
  
| 异常 | 提示 | 操作 |  
|------|------|------|  
| 图片解码失败 | 图片无法读取，请选择其他图片 | 返回相册 |  
| AI 初始化失败 | AI 功能暂时不可用 | 重试 |  
| AI 分割失败 | 未能识别清晰主体 | 重试/换图 |  
| 内存不足 | 图片尺寸过大，请选择较小图片 | 返回 |  
| 保存失败 | 保存失败，请稍后重试 | 重试 |  
| 存储空间不足 | 存储空间不足 | 清理空间后重试 |  
  
## 保存指标  
  
不再要求：  
  
```text  
保存成功率 = 100%  
```  
  
修改为：  
  
> **正常系统环境下保存成功率 ≥99.5%。**  
  
对于存储空间不足、系统服务异常等不可控情况，不计入产品自身保存失败率。

# 九、核心技术实现  
  
## 9.1 技术选型  
  
| 功能模块 | 技术方案 |  
|---------|---------|  
| UI | ArkUI / ArkTS |  
| 图片选择 | PhotoViewPicker |  
| AI 分割 | Core Vision Kit Subject Segmentation |  
| 图片处理 | Image Kit / PixelMap |  
| 并发计算 | TaskPool / Worker，最终以 API 线程限制测试结果决定 |  
| 图片保存 | PhotoAccessHelper |  
  
## 9.2 主体分割服务  
  
不要让 UI 直接调用 Core Vision API。  
  
建议封装：  
  
```text  
SegmentationService  
```  
  
内部统一负责：  
  
```text  
输入图片  
 ↓  
AI 初始化  
 ↓  
调用主体分割  
 ↓  
解析返回结果  
 ↓  
统一转换为内部 Mask  
 ↓  
校验尺寸/方向  
 ↓  
蒙版羽化  
 ↓  
输出 SubjectMask  
```  
  
建议产品内部定义：  
  
```typescript  
interface SegmentationOutput {  
  subjectMask: PixelMap;  
  confidence?: number;  
  foreground?: PixelMap;  
}  
```  
  
> 上述接口为产品内部抽象，不代表 Core Vision Kit 的实际返回结构。  
  
这样未来如果更换 AI API，不需要大范围修改 UI 和渲染逻辑。

# 十、调色算法  
  
## 10.1 内部参数结构  
  
```typescript  
interface AdjustParams {  
  brightness: number;  
  contrast: number;  
  saturation: number;  
  temperature: number;  
}  
  
interface EditState {  
  subject: AdjustParams;  
  background: AdjustParams;  
}  
```  
  
## 10.2 推荐处理流程  
  
```text  
RGB  
 ↓  
归一化  
 ↓  
亮度 / 对比度  
 ↓  
RGB → HSV  
 ↓  
饱和度  
 ↓  
色温  
 ↓  
HSV → RGB  
 ↓  
蒙版混合  
 ↓  
输出  
```  
  
## 10.3 重要原则  
  
不要把参数变化直接写回源图。  
  
错误方案：  
  
```text  
原图  
 ↓  
亮度 +20  
 ↓  
再加饱和度 +20  
 ↓  
再加色温 +20  
```  
  
推荐方案：  
  
```text  
OriginalPixelMap  
        +  
SubjectMask  
        +  
BackgroundMask  
        +  
EditState  
        ↓  
   RenderEngine  
        ↓  
 PreviewPixelMap  
```  
  
这样可以避免重复计算带来的累计误差。

# 十一、性能方案  
  
## 11.1 图片尺寸策略  
  
建议将图片处理分成三个尺寸：  
  
| 类型 | 用途 |  
|------|------|  
| 原始图 | 最终导出 |  
| 工作图 | AI/高质量处理 |  
| 预览图 | UI 实时显示 |  
  
不要在内存中长期同时保留多个原始分辨率 PixelMap。  
  
## 11.2 实时预览  
  
滑动参数时：  
  
```text  
Slider  
 ↓  
更新 EditState  
 ↓  
节流  
 ↓  
生成 PreviewRenderTask  
 ↓  
预览尺寸 PixelMap  
 ↓  
UI 显示  
```  
  
## 11.3 最终导出  
  
点击保存：  
  
```text  
OriginalPixelMap  
       +  
HighQualityMask  
       +  
EditState  
       ↓  
FinalRender  
       ↓  
ImagePacker  
       ↓  
PhotoAccessHelper  
```  
  
## 11.4 任务取消  
  
如果用户快速拖动：  
  
```text  
任务 A：亮度 10  
任务 B：亮度 20  
任务 C：亮度 30  
任务 D：亮度 40  
```  
  
不要让 A/B/C/D 全部排队执行。  
  
应尽可能：  
  
```text  
A → 取消  
B → 取消  
C → 取消  
D → 执行  
```  
  
即：  
  
> **只保证最新状态最终显示。**

# 二十五、技术文档与 PRD 的边界  
  
PRD 负责描述：  
  
- 用户要什么；  
- 产品做什么；  
- 做到什么程度；  
- 什么情况算完成。  
  
技术文档负责描述：  
  
- API 具体调用方式；  
- 具体字段；  
- PixelMap 代码；  
- Worker / TaskPool 代码；  
- 色彩算法具体公式；  
- 内存管理代码；  
- ImagePacker 具体参数。  
  
因此 PRD 不建议长期保存未经当前 SDK 验证的 API 代码。

# 二十七、产品最终核心流程  
  
V1 最终应该围绕这一条链路设计：  
  
```text  
┌───────────────┐  
│  从相册选择图片 │  
└───────┬───────┘  
        ↓  
┌───────────────┐  
│  正在识别主体  │  
└───────┬───────┘  
        ↓  
┌───────────────┐  
│  主体 / 背景   │  
│    自动分区    │  
└───────┬───────┘  
        ↓  
┌───────────────┐  
│   主体调色     │  
│ 亮度/对比/饱和 │  
│     /色温      │  
└───────┬───────┘  
        ↓  
┌───────────────┐  
│   背景调色     │  
│ 亮度/对比/饱和 │  
│     /色温      │  
└───────┬───────┘  
        ↓  
┌───────────────┐  
│   原图对比     │  
└───────┬───────┘  
        ↓  
┌───────────────┐  
│   保存到相册   │  
└───────────────┘  
```  
  
**产品核心不是“AI 抠图”，而是：**  
  
> **AI 自动生成蒙版 + 极低门槛的主体/背景独立调色。**  
  
AI 是实现手段，“简单完成局部调色”才是用户真正购买的价值。
